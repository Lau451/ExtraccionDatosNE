# Username login and admin-managed accounts

Replace email login and Supabase email invitations with username login and accounts created by an admin from the system.
Supabase Auth stays underneath as the identity engine (option A, L2): tokens, RLS (`get_rol()`/`mismo_tenant()`) and sessions are unchanged.
Delivery strategy: ask-on-risk. Branch: `feat/login-usuario-alta-admin` (from `dev`).

## Specs

User's words (L1, verbatim): "quiero que en vez de logearse con mail sea con nombre de usuario y que la creacion de usuarios la haga el admin desde el sistea que no dependa de supabase, es deir el admin crera el nombre de usuario y contraseña, se la pasa al usuario y este en el primer login le pide para cambiarla. si se olvida la contraseña se deberá contactar con el admmin para blanquear otra"

- S1 Login with username: "en vez de logearse con mail sea con nombre de usuario". The login form asks for username + password (no email field). Usernames are case-insensitive (stored lowercase), 3-30 chars of `a-z 0-9 . _ -`. Unknown username and wrong password give the same error ("Usuario o contraseña incorrectos") so usernames cannot be probed. Login goes through the backend (`POST /auth/login`), which resolves the username to the account's auth email server-side; the auth email is never sent to or shown in the browser.
- S2 Admin creates the account: "la creacion de usuarios la haga el admin desde el sistea que no dependa de supabase, es deir el admin crera el nombre de usuario y contraseña". `POST /usuarios` takes `username` + `password` (temporary) instead of `email`; no email or invitation is sent (L2: "no dependa de supabase" = no Supabase invite flow). The account gets an internal opaque auth email (`<uuid>@<internal domain>`, not derived from the username) and is confirmed immediately. Who can create, which roles and which droguería: unchanged (superadmin/admin/gerencia rules of `roles-permisos-matriz` S7). Duplicate username → 409 with a readable message. Temporary password: at least 8 characters. If the profile insert fails after the auth account was created, the auth account is deleted (no orphan).
- S3 Forced change on first login: "se la pasa al usuario y este en el primer login le pide para cambiarla". Accounts created or reset by an admin have `debe_cambiar_password = true`. While true, the frontend sends the user to a change-password screen from any route, and the backend rejects every authenticated endpoint with 403 except reading the user's own profile and changing their own password. Changing it (`POST /auth/cambiar-password` with current + new password) clears the flag. New password rules (L3: "Mínimo 8 caracteres"): at least 8 characters and different from the current (temporary) password; wrong current password → error, nothing changes. The same screen/endpoint lets any user change their own password voluntarily (from Mi cuenta).
- S4 Admin password reset: "si se olvida la contraseña se deberá contactar con el admmin para blanquear otra". `PATCH /usuarios/{id}/password` sets a new temporary password (min 8 chars) and sets `debe_cambiar_password = true`. Same authorization as activate/deactivate (superadmin/admin/gerencia, nobody on themselves, `superadmin`/`sistema` protected, gerencia only lower roles, admin/gerencia only own droguería). Self-service recovery by email is removed: no "forgot password" email flow, the login screen says to contact the administrator, and the `/reset-password` and `/accept-invite` routes are removed.
- S5 Existing users (L3: "Derivarlo del email"): a migration gives every existing user a username = the part of their auth email before `@`, normalized to the S1 format, with a numeric suffix when it collides (`jperez`, `jperez2`, ...). Existing users keep their password and are not forced to change it (`debe_cambiar_password = false`). Their auth email stays as is internally. The admin can edit any user's username afterwards (`PATCH /usuarios/{id}/username`, same authorization as S4, uniqueness enforced).
- S6 Everything else unchanged: roles, permissions, RLS, activate/deactivate, delete, role change, `PATCH /usuarios/me` (nombre/apellido) keep working as today. Users list shows the username.

- S7 Direct-database hardening (L5: "Hueco de RLS"): a user's own JWT through PostgREST must not be able to change `usuarios.debe_cambiar_password` or `usuarios.username` on any row, including an admin on their own row; only the backend (service role) and migrations/SQL run as a database owner can. Every other column and every existing RLS rule keeps working unchanged. Residual, out of scope: flagged users can still read through PostgREST under the existing RLS.
- S8 Visible rate limit (L5: "Límite de intentos visible"): when Supabase Auth answers 429 during login or while verifying the current password in `/auth/cambiar-password`, the backend returns 429 `Demasiados intentos. Probá de nuevo en unos minutos.` instead of the credentials error, and the frontend shows that message. Wrong credentials keep the S1 generic 401.
- S9 Atomic reset (L5: "Blanqueo atómico"): `PATCH /usuarios/{id}/password` sets `debe_cambiar_password = true` before changing the Auth password; if the Auth update fails, the flag is restored to its previous value and the error is returned, so the account is never left with an admin-set password and no forced change. `/auth/cambiar-password` keeps "Auth update, then clear flag" (a failure leaves the flag true: fail closed).
- S10 Regression tests (L5: "Tests de regresión"): (a) sweep every route of the presupuestacion and extraccion apps with a flagged user → 403 with the flag message except the three allowed (POST /auth/login, POST /auth/cambiar-password, own GET /usuarios/{id}), plus GET of another user's id → 403; (b) login enumeration parity: unknown user, wrong password, invalid format, empty and padded/uppercase username give identical status and body, and a successful response contains no `@`; (c) reset vs activate permission parity: for each matrix case `blanquear_password` and `cambiar_activo` raise the same exception type.

- S11 Consistency (L11: "Prolijidad: 10 y 11"): (a) the frontend `LoginResponse.expires_at` type matches the backend `int | None` (`number | null`); (b) the frontend username format error shows exactly the backend text `El nombre de usuario debe tener entre 3 y 30 caracteres: letras, números, punto, guion o guion bajo` (backend text unchanged).
- S12 Supabase failures (L11: "Errores de Supabase: 7, 8 y 9"; option text: "502-504 / 429 no-JSON / 500 JSON / fallo de get_user_by_id → respuesta 503 o 429 clara en vez de 500 o 'credenciales incorrectas'"): in login, current-password verification in `/auth/cambiar-password` and the auth-email lookup, when Supabase Auth is unreachable or answers 5xx (502-504, a JSON 500, network errors, unparseable non-429 bodies) the backend returns 503 `El servicio de autenticación no está disponible. Probá de nuevo en unos minutos.`; an Auth 429 returns the S8 429 even when its body is not JSON. Wrong credentials keep the S1 401, wrong current password keeps the 422. The answer is identical for every username (S1).
- S13 Login timing (L11: "Timing del login: 3"; option text: "Igualar tiempos (hacer siempre la consulta extra o equivalente)"): `POST /auth/login` performs the same sequence of external calls for every username — username lookup, Auth user lookup, sign-in — using fixed placeholders when the username is badly formatted, unknown or has no Auth account, so existing and non-existing usernames cannot be told apart by the number of round trips.
- S14 PostgREST reads (L11: "Seguridad DB: 5 y 6"; option text: "bloquear lectura por PostgREST a usuarios con cambio pendiente"): a user with `debe_cambiar_password = true` cannot read any table or view through PostgREST with their own JWT, except their own `usuarios` row (the backend auth dependency reads it with the user's JWT, `services/shared/auth.py:44-56`); once the flag is cleared their access is exactly as before. The backend routes allowed while flagged (S3) keep working.
- S15 Guarded id (L11: "Seguridad DB: 5 y 6"; option text: "proteger `id` en el trigger"): the 0039/0040 guard also rejects changing `usuarios.id` for any role other than the backend (service role) and database owners.
- S16 Service-client rule (L11: "12: test service client (oc_resumen)"): `tests/core/test_database.py::test_service_client_no_se_importa_en_ningun_router` passes, with `oc_resumen` meeting the rule the test states (no service client in user routers, or an allowlisted router whose repository filters `drogueria_id` explicitly); `oc_resumen` behavior for users is unchanged.

API contract (backend and frontend workers both follow it):
- `POST /auth/login` (public) body `{username, password}` → 200 `{access_token, refresh_token, expires_in, expires_at, token_type, user: {id}}` (the Supabase session fields the frontend passes to `supabase.auth.setSession`); 401 `Usuario o contraseña incorrectos`.
- `POST /auth/cambiar-password` (authenticated, allowed while flag true) body `{password_actual, password_nueva}` → 204.
- `POST /usuarios` body `{username, password, nombre, apellido, rol, drogueria_id?}` → `UsuarioOut`.
- `PATCH /usuarios/{id}/password` body `{password}` → `UsuarioOut`. `PATCH /usuarios/{id}/username` body `{username}` → `UsuarioOut`.
- `UsuarioOut` adds `username: str` and `debe_cambiar_password: bool`.
- 403 for a pending password change has message `Debés cambiar tu contraseña antes de continuar`.
